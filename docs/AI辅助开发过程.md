## 二、总体流程概览

整个开发按"先对齐需求，再生成代码，最后验证"的顺序推进，AI 在各个环节都参与，但**关键决策和最终验证由人工把关**：

```text
需求分析/文档评审
   ↓
设计规则补全 + 关键决策确认
   ↓
代码生成（约 30 个文件）
   ↓
调试与修正（测试发现 1 处问题）
   ↓
测试与端到端验证（11/11 通过）
   ↓
文档产出（演示话术、AI 过程记录）
```

## 三、各阶段详细过程

### 3.1 需求分析与文档评审

**给 AI 的输入（关键 Prompt）：**

```text
读一下我的"wendang"文件夹
```

```text
需要你协助我完成此项目，代码部分写在"daima"文件夹，
你先看看 wendang 还有需要优化完善的吗
```

**AI 做了什么：**

- 通读了两份文档（`readme.md` 项目说明、`zhidaowenjian.md` 开发设计文档），提炼出项目目标、技术栈、核心业务闭环；
- 对文档做了**审查**，指出了 11 处需要完善的问题，并划分了优先级：
  - 🔴 关键缺口 4 项：营业时间未定义、"completed 状态无人触发"、删除房间的外键冲突、`init_db.py` 与 Flask-Migrate 依赖不一致；
  - 🟡 一致性问题 4 项：forms.py 与依赖不符、AI 推荐功能定位含糊、"重复预约"与冲突检测重叠、时间段热度统计口径未定；
  - 🟢 细节 3 项：人数未校验下限、过去日期预约的取消、tests 目录缺失。

**人工验证：**

- 逐条核对 AI 指出的问题，确认哪些是真实的、必须补的；
- 拍板采用 AI 建议的"先修订文档再写代码"的顺序（方案 A），避免边写边返工。

### 3.2 设计规则补全与关键决策确认

**AI 做了什么：**

- 按确认的方案，把 4 个关键缺口 + 一致性问题一次性补进两份文档：
  - 新增全局营业时间 08:00–22:00（`config.py` 配置）；
  - 新增预约状态流转机制 `booked → cancelled / completed`，明确"过期自动完成、无需定时任务"；
  - 新增规则 R11（过期预约不可取消）、R12（有预约记录的房间不可删除）；
  - 统一依赖为 4 个包，初始化统一走 `python init_db.py`，去掉 Flask-Migrate；
  - 修正冲突提示话术（本人 vs 他人）、时间段热度口径、使用率公式等。

**关键决策（AI 提出选项，人工选择）：**

| 决策点 | AI 给出的选项 | 人工选择 |
|---|---|---|
| 营业时间如何实现 | 全局常量 / 每房间单独配置 | **全局常量**（最简单，符合课程定位） |
| AI 推荐房间是否实现 | 先不做占位 / 简单规则推荐 / 接入真实 LLM | **先不做，留空占位**（不计入必做） |

**人工验证：**

- 检查修订后的文档是否自洽、是否覆盖题目必做功能；
- 确认这两项决策后，才让 AI 开始写代码。

### 3.4 调试与修正

**给 AI 的输入（关键 Prompt）：**

```text
运行一下
```

**AI 做了什么 + 人工验证（发现 1 处问题并修正）：**

- AI 创建虚拟环境、安装依赖、运行 `pytest`，得到 **11 条测试 1 条失败**；
- 定位失败原因：不是业务代码问题，而是**测试用例自身写错了**——用 admin 账号去验证"越权取消"，但设计上管理员本来就允许取消任何预约；
- 修正方式：新增一个普通学生账号 `student2` 作为"非本人的普通用户"来测试越权，测试改为符合真实业务语义；
- 复跑后 **11/11 全部通过**。

> 这体现了"AI 生成 → 人工审查 → 发现并修正"的完整闭环，也说明测试不能只看"过没过"，还要看"测的语义对不对"。

### 3.5 测试与端到端验证

**AI 做了什么 + 人工验证：**

1. **单元测试**：覆盖冲突检测、边界不冲突、取消释放、越权取消、过期完成、营业时间、容量、过去日期等 11 个用例，全部通过；
2. **数据库初始化**：`python init_db.py` 成功建表并生成默认账号 + 4 个演示房间；
3. **端到端冒烟测试**：用 Flask test client 走完整 HTTP 流程——登录 → 创建预约 → 冲突拦截 → 取消 → 统计 API → 删除保护，全部符合预期；
4. 冒烟测试中又发现一处**断言写错**：同用户重复预约的提示应是"您已预约该时段"，而断言写成了"该时间段已被预约"（后者是他人冲突的话术）。二次验证确认两种话术各自正确，业务逻辑无误。

**验证结果汇总：**

| 验证项 | 结果 |
|---|---|
| 单元测试 | 11/11 通过 |
| 数据库初始化 | 成功 |
| 端到端 HTTP 流程 | 全链路通过 |
| 冲突提示（本人 / 他人） | 分别正确返回 |

## 五、AI 使用的体会与反思

1. **AI 适合"生成初稿"，不适合"直接交付"**：冲突检测函数、页面模板、测试用例都是 AI 生成的初版，但最终都要经过人工审查和验证——本次就因此发现了 2 处测试/断言错误，若直接照单全收会导致验收翻车。

2. **先对齐规则再写代码，避免返工**：本次先在文档层面补齐营业时间、completed 机制、删除策略，再让 AI 写代码，整个过程没有出现大规模返工。

3. **验证要"看语义，不能只看结果"**：第一次测试"过没过"之外，更要看测试的语义是否和业务一致（例如"越权"应该用普通用户而非管理员来测）。

4. **AI 是加速器，人是责任人**：AI 把重复性劳动（CRUD、模板、测试骨架）大幅提速，但需求取舍、关键决策、最终正确性仍由人负责。
