## 一、演示前准备（开始前 5 分钟）

1. **启动项目**：进入 `daima` 目录，激活虚拟环境后运行 `python run.py`，浏览器打开 `http://127.0.0.1:5000`。
2. **确认数据库已初始化**：运行过 `python init_db.py`，存在 4 个演示房间（A101 / A102 / B201 / B202，其中 **B202 是"维护中"**，用于演示）。
3. **准备两个浏览器窗口**：一个普通窗口 + 一个无痕窗口，分别登录 `student` 和 `admin`，方便演示"本人 / 他人"两种冲突提示。
4. **记好今天和明天的日期**：预约必须用**未来日期**（如明天），过去日期会被拦截。

> 可选：想更真实地演示"两个学生抢同一时段"，可新增第二个学生账号：
> ```bash
> # 在 daima 目录、激活 venv 后执行
> python -c "from app import create_app, db; from app.models import User; app=create_app(); \
> exec(\"with app.app_context():\n    u=User(username='student2', name='学生2'); u.set_password('student123'); db.session.add(u); db.session.commit()\")"
> ```

## 三、分场景详细步骤与话术

### 场景 0：开场（1 分钟）

**话术：**

> 各位老师好，我做的项目是"自习室/会议室预约系统"，对应选题第 15 题。它解决的是校园共享空间——自习室、实验室、会议室——按时间段预约的需求，核心是解决"同一房间同一时段被重复预约""取消后时段没有释放"这类问题。
>
> 技术栈是 Flask + SQLite + Bootstrap + ECharts。接下来我演示完整的业务闭环，并重点验证几条业务规则。

---

### 场景 1：登录与房间浏览（1 分钟）

**操作步骤：**
1. 打开 `/login`，用 `student / student123` 登录；
2. 展示房间列表卡片（名称、位置、容量、设备、状态）；
3. 指出 **B202 显示"维护中"**。

**话术：**

> 我先用学生账号登录。系统区分学生和管理员两种角色。登录后进入房间列表，可以看到每个房间的容量、设备、状态。注意 B202 是"维护中"状态，这样的房间是不能预约的，待会儿我会演示这一点。

---

### 场景 2：查看可用时段（1 分钟）

**操作步骤：**
1. 点进 **A101** 详情；
2. 日期默认是今天，改成**明天**，点"查询可用时段"；
3. 展示 08:00–22:00 逐小时时段格子，当前全部绿色"空闲"。

**话术：**

> 进入房间详情，可以按日期查看该房间的可用时段。系统把营业时间 08:00 到 22:00 按小时划分，绿色是空闲、红色是已预约。今天这个房间没有预约，所以全是空闲。营业时间是在配置文件里全局配置的。

---

### 场景 3：创建预约（1 分钟）

**操作步骤：**
1. 点"预约该房间"；
2. 填：日期 = 明天，14:00–15:00，人数 3，用途"自习"，提交；
3. 出现绿色"预约成功"，跳转到"我的预约"。

**话术：**

> 我预约明天 14:00 到 15:00，人数 3 人。提交后预约成功，我的预约列表里多了这条记录，状态是"已预约"。

---

### 场景 4：时间冲突检测（核心，2 分钟）

**操作步骤：**（利用两个窗口切换身份）

1. **本人重复**：学生窗口再约 A101 的 14:30–15:30 → 提示 **"您已预约该时段"**；
2. **他人冲突**：切到 admin 窗口，对 A101 约 14:30–15:30 → 提示 **"该时间段已被预约"**；
3. **边界不冲突**：再约 15:00–16:00 → **成功**（首尾相接不算冲突）。

**话术：**

> 这是本项目的核心业务规则：同一房间、同一天，时间段有重叠就必须拒绝。判定公式是"已有开始时间小于新结束时间，并且已有结束时间大于新开始时间"。
>
> 我现在约 14:30 到 15:30，和刚才 14:00–15:00 重叠，系统拒绝并提示。换管理员账号再试同一时段，同样被拒——因为冲突检测只看房间和时间，不看是谁。
>
> 再看一个边界：约 15:00 到 16:00，正好接在 15:00 后面，首尾相接不算冲突，可以成功。这说明时间比较用的是半开区间，边界处理是对的。

---

### 场景 5：取消 + 时段释放（1 分钟）

**操作步骤：**
1. 学生窗口进"我的预约"，点 14:00–15:00 那条的"取消"，确认；
2. 提示"预约已取消"，状态变"已取消"；
3. 回到房间详情，明天该时段重新变绿（空闲）；
4. 再次预约 14:00–15:00 → **成功**（证明时段已释放）。

**话术：**

> 学生取消自己的预约后，记录变成"已取消"，同时该时段被释放。看，明天 14:00–15:00 又变回空闲，可以重新预约。这就是"取消后时段自动释放"，保证数据闭环。

---

### 场景 6：异常场景演示（1 分钟）

挑 3–4 个快速演示，每个都是提交后出现**红色错误提示**：

| 操作 | 预期提示 |
|---|---|
| 开始 16:00、结束 15:00 | 开始时间必须早于结束时间 |
| 日期选昨天 | 不能预约过去的日期 |
| 人数填 20（A101 容量 10） | 人数超过房间容量 |
| 预约 B202（维护中） | 该房间正在维护，暂不可预约 |

**话术：**

> 系统对非法输入都有明确提示。开始时间晚于结束时间、预约过去的日期、人数超容量、预约维护中的房间，都会在前端和后端双重校验拦截，给出中文提示。

---

### 场景 7：管理员房间管理（1 分钟）

**操作步骤：**（切 admin 窗口）

1. 进"房间管理"，新增房间 C301（容量 12、有投影仪）→ 列表出现；
2. 编辑 A101 容量改成 12 → 保存生效；
3. 尝试删除 A101（已有预约）→ 提示 **"该房间存在预约记录，无法删除"**；
4. 删除刚才新增的 C301（无预约）→ 成功。

**话术：**

> 管理员可以新增、编辑、删除房间。注意：有预约记录的房间不能删除，防止破坏历史数据；没有预约的房间可以正常删除。

---

### 场景 8：全部预约查询（1 分钟，可选）

**操作步骤：**
1. 进"全部预约"，按房间 / 状态 / 日期筛选；
2. 展示刚才 student 的预约记录。

**话术：**

> 管理员可以看到所有用户的预约，并支持按房间、状态、日期筛选。

---

### 场景 9：统计看板（2 分钟）

**操作步骤：**
1. 进"统计看板"，展示 4 张图：各房间预约次数、房间使用率、预约状态分布、时间段热度；
2. 指出数据随刚才的操作变化。

**话术：**

> 统计看板用 ECharts 展示四类数据：各房间预约次数、使用率、状态分布、时间段热度。这些数据是实时从数据库聚合的，刚才创建的预约已经体现在图里，说明预约数据真正落库并形成闭环。

**操作步骤：**
1. 打开 `instance/reservation.db`（用 SQLite 浏览器或命令行），展示 `reservations` 表里的记录。

**话术：**

> 最后看一下数据库。打开 reservation.db，能看到 users、rooms、reservations 三张表，预约记录真实落库，状态、取消时间都记录了。这证明系统不是只做前端，数据是持久化的。

## 五、常见翻车点与应对

| 风险 | 应对 |
|---|---|
| 忘记用未来日期 | 提前记好明天日期；真忘了会提示"不能预约过去的日期"，顺势变成异常演示 |
| 冲突提示背混 | 本人重复 = **您已预约该时段**；他人冲突 = **该时间段已被预约** |
| 统计图空白 | 先进房间建几条预约，再进统计看板 |
| 断网时前端样式/图表失效 | Bootstrap、ECharts 走 CDN，需联网，提前测试；可让助手提前下载到本地 |
| 演示中途数据库弄脏 | 提前备份，或重新跑 `python init_db.py` 重置 |
| 两个窗口登录串号 | 用无痕窗口 + 普通窗口隔离 cookie，登录前确认右上角用户名 |
